# 芒果端辅助 · 26.2 协议版

> 当前版本 **V6.4（6.4.0）**：桥接下线成功后，自动使用同一账号独立连接原服务器；设置可关闭，或扩展到普通游戏下线。配套 **桥接 Mod 1.7.0** 增加真实离线证据，不把本地桥接断开或游戏重新配置误作下线。继续保持未签名，保留双开独立端口和账号配置。见 [V6.4 发布说明](docs/RELEASE-6.4.md) 和 [桥接安装说明](docs/CLIENT_BRIDGE_SETUP.md)。

> 不用启动 Minecraft，直接以玩家身份连上服务器 —— **支持正版验证服（`online-mode=true`）**，用你自己的微软账号免密登录。
>
> 前身为「MC免客户端登录器」，自 **2.4.14** 起改名为「芒果端辅助」。内部 appId 与固定数据目录保持不变，老用户升级后原账号、服务器、欢迎预算与桥接配对继续可用；旧在线历史文件不会再追加，也不会被自动删除。

## 最新版本说明

**V6.1**：在“设置 → 桥接下线”选择或填写目标 ID 并启用；当前服实际名单出现该玩家后，游戏再次确认其在线，再执行原版下线流程，停止辅助监听和重连。已经在线的目标也会触发；聊天提及不触发下线。关注页在可见、聚焦时自动将已展示的当前服消息标为已读，后台新消息保留未读。不再提供离线演练或手动已读按钮。监测名单相关发言、@、正文提及和封禁广播写运行日志，不新增说明面板。使用新下线能力必须将目标实例旧桥接 Mod 替换为 1.5.0，配对文件沿用。详见 [发布说明](docs/RELEASE-6.1.md)。

**V6.0**：动作过程保留结构化原因，识别、等待、提交和服务端确认分开显示；关注页显示当前服动作及重要消息，可定位只读原消息。按服务器隔离自动化、零点命令、快捷指令、监测名单、显示筛选和提醒。系统通知默认关闭、静音时段只记未读、3 秒合并、正文默认隐藏；便携版系统展示需要实机确认。离线演练复用实际红包/欢迎判断，不发送、不改变真实额度，不预测到账。历史记录 7 天与 128 MiB 双预算，后台停止聊天/日志 DOM 更新和资源采样；休眠取消动作，恢复后手动重连。详见 [发布说明](docs/RELEASE-6.0.md)。

**V5.8**：桥接连接的 `autoPurchaseEnabled` 默认为 `false`；进服、重连、签到完成及跨天均不自动触发收购菜单或 Shift+F。手动“获取收购价”仍可不限次执行，已有价格快照和次数保留；独立连接自动采集不变。只需更新登录器，不需更换 Mod。详见 [发布记录](docs/RELEASE-5.8.md)。

**V5.7**：接入本地整合包的自定义物品中文词表；独立连接解析嵌套 `translate` 组件，农作物收购不再显示已知翻译键，金银星级随名称恢复。已有快照只在内存中转换显示，不重新采集、不改写原文件或次数、价格和时间；未知名称保持原文。名称提示保留原始翻译键和物品 ID。桥接无需更新。详见 [发布记录](docs/RELEASE-5.7.md)。

**V5.6**：日志定位到主菜单 ready 但 stateId=-1 被点击保护拒绝；现兼容并原样回传服务端 -1，保留窗口、光标、频率及重复点击保护。修复独立连接收购导航，桥接无需更新。详见 [发布记录](docs/RELEASE-5.6.md)。

**V5.5**：手动“重新获取”不受每日次数限制，自动获取每天最多成功 1 次；手动与自动分别计数。旧版本当天已完成的记录不再阻挡手动采集。成功更新快照；失败保留上次数据且不增加次数。独立连接和桥接均适用，无需更换 Mod。详见 [发布记录](docs/RELEASE-5.5.md)。

**V5.4**：独立连接自动采集菜单不再出现在软件弹窗中；失败也只显示原因，之后同一菜单的刷新不会重新弹窗。连续刷新不再重置 700 ms 导航等待，到点按最新状态核验并点击。手动菜单和成功的桥接流程保留原行为，桥接无需更换 Mod。详见 [发布记录](docs/RELEASE-5.4.md)。

**V5.3**：参考用户成功的 MenuWatch 源码，Shift+F 改为跨 tick/延时动作，先保持潜行再换副手；导航按实时下发的唯一入口名称查找，不再固定格号。收到公会菜单立即停止并记录实际标题，超时日志注明预期和实际界面。独立连接无需 Mod，桥接需 1.4.0。详见 [发布记录](docs/RELEASE-5.3.md)。

**V5.2**：聊天、运行日志、在线玩家之后新增“每日收购”。独立连接通过 Shift+F 等效协议动作打开主菜单；桥接需要 Mod 1.3.0。只读取系统收购与农作物收购，不采集鱼类、不出售物品；两类各 15 个商品位读取完整并保存成功后记为当天 1 次，失败保留 0 次。上线补采、签到后采集及次日重置共用服务器和账号隔离的记录。详见 [发布记录](docs/RELEASE-5.2.md)。

## 正版验证是怎么实现的

`online-mode=true` 的服务器要求客户端完成**加密握手**，这是纯技术流程，不是"破解"：

```
客户端                                    服务器
  │  Login Start (名字 + UUID)              │
  │ ──────────────────────────────────────► │
  │                                          │
  │  Encryption Request                      │
  │  (serverId, RSA公钥, verifyToken,        │
  │   shouldAuthenticate=true)               │
  │ ◄──────────────────────────────────────  │
  │                                          │
  │  ① 生成 16 字节随机 sharedSecret         │
  │  ② SHA1(serverId+secret+公钥DER) → 签名  │
  │  ③ 把签名提交给 Mojang 会话服务器  ──────►│  Mojang
  │     (证明"这个账号确实要进这个服")        │  验证通过
  │  ④ RSA 加密 secret + token               │
  │ ──────────────────────────────────────► │
  │                                          │
  │  双方用 sharedSecret 做 AES-128-CFB8     │
  │  此后所有包全程加密                       │
  │ ◄──────────────────────────────────────  │
  │                                          │
  │  Set Compression → Login Success → Play  │
```

### 微软账号登录链（4 步）

```
1. 微软 OAuth 2.0 授权码 + PKCE
      ↓ 拿到 Microsoft access_token / refresh_token
2. Xbox Live 认证 (user.auth.xboxlive.com)
      ↓ 拿到 XBL token
3. XSTS 授权 (xsts.auth.xboxlive.com)
      ↓ 拿到 XSTS token
4. Minecraft 认证 (api.minecraftservices.com)
      ↓ 拿到 Minecraft access_token → 查 profile 得到真实 UUID
```

`refresh_token` 就是"免密"的关键 —— 授权一次后，之后所有的 token 都能静默换新。

### 实现细节（踩过的坑）

| 点 | 要点 |
|---|---|
| **serverId 签名** | `SHA1(serverId + sharedSecret + 公钥DER)`。**Java 的 BigInteger 是有符号大端**，若十六进制首位 ≥ 8，必须补 `-` 前缀 —— 少这一位 Mojang 直接 403 |
| **公钥格式** | 服务器给的是 X.509 SubjectPublicKeyInfo。若解析失败，回退成 PKCS#1 |
| **加密算法** | **AES-128-CFB8**（不是 CBC、不是 GCM）。Node 内置 `aes-128-cfb8` 直接可用 |
| **RSA 填充** | `RSA_PKCS1_PADDING`，不是 OAEP |
| **加密时机** | Encryption Response **明文发出**，发出**之后**立刻切到加密，顺序不能错 |
| **16 字节 secret** | 必须 `crypto.randomBytes(16)`，不能自己拼 |

### ① 离线模式 —— 在本机真实 26.2 服务器上跑通

```
[TCP] 已连接 127.0.0.1:25599
[登录] 以 BaiXu 发起登录（离线模式）
[压缩] 阈值 = 256
[登录成功] BaiXu (ba9b032e-db6d-37bf-ae20-dbb82b22e4cf)
[配置] 完成，进入游戏
[世界] 已进入世界，实体ID = 1
[坐标] 6.5, -60.0, 9.5
```

**服务端日志（决定性证据）：**
```
BaiXu[/127.0.0.1:3168] logged in with entity id 1 at (6.5, -60.0, 9.5)
BaiXu joined the game
<BaiXu> 测试：这是一条来自免客户端工具的聊天
BaiXu left the game
```

保活压测：连续在线 60 秒，**零掉线**。

### ② 正版模式 —— 在真实 `online-mode=true` 服务器上跑通加密握手

对准一个真实的 `online-mode=true` 26.2 服务器（端口 25611）实测：

```
[握手] 已发送 Handshake
[登录] 以 BaiXu 发起登录（正版账号认证）
[加密] 收到 Encryption Request
       serverId=  (空)
       verifyToken= 4 字节
       shouldAuthenticate= true
[加密] 生成 sharedSecret，计算签名 SHA1...
[加密] 提交 Mojang 会话服务器...
       ← HTTP 403 ForbiddenOperationException（用的是测试假 token，符合预期）
```

**关键点**：客户端**正确解析了真实服务器的加密请求**，完成了 `sharedSecret` 生成、SHA1 签名、AES-128-CFB8 上下文建立、RSA 加密回包，并走到了 Mojang 会话注册这一步。403 是因为测试用的是**故意伪造的 token** —— 真实账号的 token 会通过并完成握手。

**这证明加密握手实现是正确的。** 换成真实微软账号即可进服。

## 功能：服务器聊天查看（v2.4.0 新增）

**你要的效果**：连上服务器后，能看到服务器里的聊天内容。

界面上「运行日志」旁边多了个 **「聊天」页签**（默认就是它）：

| 显示 | 来源 | 样式 |
|---|---|---|
| 玩家发言 | `player_chat` | 青色，带说话人名字 |
| 服务端广播（`/say`、插件公告） | `profileless_chat` / `system_chat` | 蓝色 |
| 快捷栏提示（action bar） | `system_chat(isActionBar)` / `action_bar` | 灰色斜体 |
| 自己发的消息 | —— | 黄色 |

- 聊天独立于运行日志：以前两者混在一起，服务器一广播就被网络日志冲上去，想看一眼谁说了话得往上翻半天。
- 保留最近 **800 条**，切到日志页时新消息会累积**未读计数**气泡，不会静默溜走。
- 运行日志里仍保留一份（便于事后翻完整时序）。

### ❗❗ 这一轮挖出的真凶：网络 NBT 是「匿名格式」

**症状**：连上服务器后，**一条聊天都收不到**（`onChat` 回调次数 = 0），但网络日志一切正常。

**排查方式**（严格只收不发，不会触发任何服务端风控）：
本地起真实 26.2 服务端 → 客户端只连接**不发言** → 从**服务端控制台**执行 `say` / `tellraw` 广播
→ 在收包处 dump 原始字节。

抓到的真实字节：

```
0x79 system_chat（tellraw {"text":"PROBE_TELLRAW","color":"gold"}）
79 0a 08 0005"color" 0004"gold" 08 0004"text" 000d"PROBE_TELLRAW" 00 00
   ↑
   compound 之后**直接就是子标签** —— 根节点没有名字

0x21 profileless_chat（控制台 say）
21 08 0012"PROBE_SERVER_SAY_1" 05 08 0006"Server" 00
   └─── message(NBT) ───┘     └type┘ └── name(NBT) ──┘ └target=空┘
```

对照官方 `protocol.json`：字段类型是 **`anonymousNbt`** —— 网络 NBT **没有根名**。
而 `nbt.js` 的 `readRoot()` 却去读一个根名字：把 `08 00` 当成长度 `0x0800 = 2048` → 越界 → 抛错
→ 被 `decodeComponent` 的空 `catch` 吞掉 → **返回 null → 聊天静默消失**。

**最难受的地方**：原来的 NBT 测试**自己构造带根名的数据**，于是测试和实现犯了同一个错 ——
测试全绿，真机上所有 NBT 全解不出来。这类"自证式测试"是最危险的。

修复：`readRoot()` 不再读根名（网络 NBT 直接就是 `[type][payload]`）。
修复后同一条抓包立刻能解析：`onChat` 回调从 **0 次** 变成 **4 次**，中文、`extra` 拼接全部正确。

### 顺带修掉的两处聊天缺陷

| 包 | 官方定义 | 旧代码 | 后果 |
|---|---|---|---|
| `player_chat` (0x41) | `signature: option[buffer 256]` | 只读了 bool，**没跳过 256 字节** | 签名存在时正文错位 → 消息丢失 |
| `profileless_chat` (0x21) | 独立包 | **完全没处理** | 控制台 `/say`、NPC、插件广播一条都收不到 |

另外 `loginDisconnect` 的 reason 类型是 **string**（不是 NBT，与 configuration/play 阶段不同），
旧代码按 NBT 解析，所以被拒时看不到原因；已一并修正。

### 新增的静态一致性检查

本机沙箱跑不了 GUI 自检（Electron 起不来会挂），于是补了 `src/ui_consistency_test.js`：
纯静态解析三个文件，抓出「renderer 引用了 HTML 里不存在的 id」「preload 没暴露的方法被调用」
「动态 class 在 CSS 里没定义」这类**接线失配**。它跑得比 GUI 快得多，且能在提交前拦住问题。

> 顺带清掉 3 个既不被 JS 也不被 CSS 使用的死 `id`（`pill-account` / `skin-box` / `conn-stats`）。

## 修复：连真服被拒 multiplayer.disconnect.unverified_username（v2.4.1）

**症状**（接 mc.example.invalid 时）：
```
[验证] Mojang 登记成功，服务端将反查并放行
[被拒绝] multiplayer.disconnect.unverified_username
```
能连上、能完成加密握手、也能向 Mojang 登记，但服务端 `hasJoined` 反查失败。

**根因**：**两条微软授权链并发**。

启动自动登录（v2.3.0 引入）会走一条 `微软→XBL→XSTS→MC` 完整授权链。
如果用户在它**跑完之前**就点了「连接」，`doConnect` 一看 `account` 还是 null，
**又独立开了一条同样的完整授权链** —— 9 秒内连发两套完整授权。

两条链并发 → 微软侧会话串扰 → 服务端反查失败。
（v2.1.1 能进，是因为当时只有「点连接」这一条链，没有启动自动登录。）

**修复**：`ensureAccount()` —— 全进程同一时刻只允许一条授权链。
- 已登录 → 直接返回
- 正在登录 → 并发调用方 `await` 同一个 Promise，共享结果，不再各开一条

自动登录、连接前续期，全部走这一个入口。

## 功能：启动时自动登录账号（v2.3.0 新增，v2.3.1 收窄）

**你要的效果**：打开软件 → 自动免密续期微软账号 → 点「连接」就能进服，不用再手点登录。
右上角有开关「**启动时自动登录账号**」，默认开启，随时可关。

> **v2.3.1 变更**：按用户要求**移除了"自动连接上次的服务器"**。
> 软件只负责把账号登好，**连哪台服由你自己点** —— 程序不替你决定进哪个服务器。

### 两层语义（失败也不会卡住界面）

| 层 | 行为 | 失败时 |
|---|---|---|
| 1. 静默续期账号 | 只用本地 `refresh_token` 换新令牌 | 打日志提示手动登录，**不弹授权码** |
| 2. 无账号 | 什么都不做 | 界面照常可用 |

**服务器不在自动流程里** —— 程序只把账号准备好，进哪台服由用户点「连接」决定。

> 边界由源码级断言守住（`src/autologin_test.js` 段 [G]）：
> `runAutoLogin()` 函数体里**不得出现 `doConnect` 调用**，也不得引用 `lastServer`。
> 以后谁把自动连接加回来，自检会立刻报警。

### ❗核心设计：`silentOnly` —— 防止"静默卡死 15 分钟"

这是本轮最关键的改动。启动自动登录调的是 `auth.login({ silentOnly: true })`。

**为什么必须加这个开关**：不加它时，一旦本地凭据失效，`login()` 会掉进**设备代码流**——
申请一个 8 位短码、**自动打开浏览器**、然后循环轮询最多 **15 分钟**。
用户看到的现象是「软件卡住了」，而他根本不知道自己在等什么。

加了这个开关后，静默模式在"缓存不可用"时**直接抛错**，由上层降级为一行日志提示。

**两条否定式断言守住了这个不变量**（`src/autologin_test.js`，全部场景都验）：

```
❗静默模式下，设备代码端点一次都不能被调用
❗静默模式下，绝不能自动打开浏览器
```

覆盖场景：无凭据 / 凭据失效 / 凭据有效 / 缓存文件损坏 / 缓存缺 refresh_token。
另有**对照组**证明不加开关时确实会走设备代码流并弹浏览器 —— 证明这个测试真的有效，
而不是"因为什么都没做所以没报警"。

### 顺带修的隐患：测试会覆盖真实凭据

排查中发现 `devicecode_test.js` **没有隔离凭据路径**：`auth.js` 在模块加载时就用
`%APPDATA%\.mc-noclient\accounts.json` 算好了 `TOKEN_CACHE`，所以只要测试走到
"登录成功"分支，就会把用户**真实的 refresh_token 覆盖成测试假值** ——
用户下次打开软件就得重新走一遍授权。

当前用例恰好在 Xbox 阶段就抛错、还没到写缓存，所以没出事；但这是颗地雷
（以后补一个"全链路成功"的用例就会踩爆）。已加上临时目录隔离。

> 验证方式：把 `%APPDATA%\.mc-noclient` 整个移开 → 跑完整套测试 → 确认它**没有被重新创建**
> → 再还原。这套检查应该成为以后的习惯。

## ❗ 第三关键 BUG：添加的服务器"每次重开就消失"（v2.2.1 修复）

**症状**：用户添加服务器后，界面显示正常；但关掉程序再打开，**自己加的服务器不见了**，
只剩默认那条——而账号登录状态却记得住。反复添加，反复消失。

**根因是两个缺陷叠加**：

### 缺陷 1（真凶）：配置写在"每次都会变"的目录里

旧代码：

```js
const DATA_DIR = app.isPackaged
  ? path.join(path.dirname(process.execPath), 'data')   // ❌ exe 同级
  : ROOT_DIR;
```

问题出在 **便携版（portable）**：它运行时会把自身解压到一个**随机临时目录**再启动，
`process.execPath` 就指向那个临时目录。于是：

```
第 1 次运行 → 解压到 %TEMP%\abc123\ → 配置写进 %TEMP%\abc123\data\config.json
退出       → %TEMP%\abc123\ 被清理，配置一起没了
第 2 次运行 → 解压到 %TEMP%\xyz789\ → 去 %TEMP%\xyz789\ 找配置 → 空的 → 显示默认
```

**用户看到的正是"我加的服务器没了"**，而且安装版/开发模式都正常，只有便携版复现——
这类"只在某一种运行形态下出问题"的 bug 最难察觉。

> 对比：`src/auth.js` 把账号缓存写在 `%APPDATA%\.mc-noclient\`（**固定路径**），
> 所以账号能记住、服务器列表记不住 —— 这个差异是定位问题的关键线索。

### 缺陷 2：保存失败被静默吞掉

```js
function saveConfig(cfg) {
  try { ...; return true; }
  catch (e) { return false; }     // ❌ 错误信息直接扔掉
}
```

界面那边也是"发射后不管"：`window.api.saveConfig(cfg)` **不 await、不看返回值**。
所以就算真写盘失败（磁盘满 / 权限 / 路径异常），用户也完全无感，只会觉得"又没保存上"。

### 修复

**① 配置统一放到用户级固定目录** `app.getPath('userData')`（即 `%APPDATA%\<productName>`）：

| 运行形态 | 旧位置 | 新位置 |
|---|---|---|
| 便携版 | `%TEMP%\<随机>\data\` ❌ 每次变 | `%APPDATA%\MC免客户端登录器\` ✅ 固定 |
| 安装版 | `安装目录\data\` | `%APPDATA%\MC免客户端登录器\` ✅ |
| 开发模式 | 项目根目录 | `%APPDATA%\MC免客户端登录器\` ✅ |

**② 首次运行自动迁移旧配置**（只读不删源文件，不擅动用户数据），多个旧位置依次尝试，坏的就跳过。

**③ 保存改为「原子写 + 结果回传」**：先写 `.tmp` 再 `rename`（避免半个坏文件），
返回 `{ok, error, path}`；界面 `await` 后检查结果，**失败立刻弹提示并在日志里写明原因**。

**④ 读取失败不再静默**：以前 `catch` 里直接返回默认配置，用户以为"服务器没了"；
现在把错误原因带回界面显示。

### 这个 bug 的教训

我把配置的**纯逻辑抽到了 `src/configstore.js`**（路径由调用方注入），
这样它就能在纯 Node 下被完整测试。新增 **17 个回归用例**，其中两个专门守住这次的坑：

- 「模拟便携版：配置在固定目录时，换 exe 解压目录不受影响」
- 「反面对照：旧逻辑（写进随机目录）确实会丢配置」← *用例本身就在解释当初为什么错*
- 「目标路径不可写时，save 返回 ok:false 且带原因」

原来这套逻辑内联在 `main.js` 里、依赖 Electron 的 `app` 对象，**纯 Node 跑不起来 → 根本没法测
→ 只能等用户发现**。抽出来之后，这类问题就能在自检阶段拦住了。

此外还在真实 Electron 主进程里做过一次端到端验证：
「启动 → 加服务器 → 保存 → 关掉 → 再启动」，确认 `servers=2`、目标服务器仍在、用户名保留。

## 功能：CPU / 内存占用监控（2026-10-07 新增）

界面右上方新增「资源占用」卡片，每秒刷新一次：

| 显示 | 含义 |
|---|---|
| **CPU** + 折线 | **整个软件**（所有 Electron 进程求和）占整机 CPU 百分比 |
| **内存** + 折线 | 整个软件的常驻内存（各进程 workingSetSize 求和） |
| 系统 CPU / 内存 | 顶栏右侧小字：整机 CPU 占用 + 已用/总内存 |
| 「明细」按钮 | 展开按进程拆分：主进程 / 界面进程 / GPU / 工具进程 的 CPU 与内存 |

### 实现要点（为什么不用第三方库）

- **不引 `systeminformation`**：它会带来几十 MB 依赖且含原生模块，打包后极易出问题。
  用户要的是「**这个软件**占了多少」，Electron 的 `app.getAppMetrics()` 正好能给**按进程拆分**的数据。
- **双运行环境**：主进程走 `getAppMetrics()`；纯 Node（自检 / CLI）下 `app` 不存在，
  自动降级用 `process.memoryUsage()` + `os` 采样 —— 同一套代码两种环境都能跑、都能被测试。
- **CPU 差分口径**：进程 CPU% = `ΔCPU时间 / Δ墙上时间 / 核心数 × 100`
  （与任务管理器"占整机百分比"一致）。时间基准用 `process.hrtime` 的**单调时钟**，
  避免系统时间被校准时算出天文数字或负数。
- **折线手绘**：`<canvas>` 直接 2D 绘制，按 `devicePixelRatio` 缩放，高分屏不发虚，零依赖。

### 本轮又抓到一个真 BUG（靠测试发现）

写 `monitor_test.js` 时对不上数，反查发现：**`ProcessMetric.memory` 是顶层字段，与 `cpu` 平级**，
不是 `cpu.memory`。写成 `cpu.memory.workingSetSize` 会**静默得到 0 字节** ——
界面上表现为「所有子进程内存都显示 0 B」。

已核对 Electron 官方 `ProcessMetric` / `MemoryInfo` 文档并修正为 `m.memory.workingSetSize`，
且 `workingSetSize` 单位是 **KB**（×1024 转字节）。
在主进程实测验证：主进程 `workingSetSize=132028` KB → 显示 128.9 MB，与 `process.memoryUsage().rss` 吻合。

## 重度审查记录（2026-10-07）

开发完成后做了一轮对抗性审查，**挖出并修复了 1 个会导致正版登录"静默失败"的关键 BUG**，以及十余个健壮性问题。

### ❗ 关键 BUG：压缩阈值竞态（正版登录静默失败的真凶）

**症状**：在 `online-mode=true` 的服务器上，客户端打印 `[压缩] 阈值 = 64` 之后就再无反应 —— 没有报错、没有断开，就是卡住。而且**只在部分服务器上复现**。

**根因**：Minecraft 的压缩是"中途启用"的：服务端在登录阶段发一个 `Set Compression` 包，**此后的所有包都按压缩格式封装**。问题在于 TCP 不保证包边界 —— `Set Compression` 和紧随其后的 `Encryption Request` 完全可能落在**同一个 TCP 段**里。

原来的代码是"先把整个 chunk 解完、再逐个处理"：

```js
// ❌ 旧代码：一次性解完
for (const pkt of this.decoder.push(chunk)) this.handlePacket(pkt);
```

于是排在 `Set Compression` 之后的那个包，仍然用**旧的** `threshold = -1` 去解 —— 一个压缩帧被当成未压缩帧解析，解出 185 字节垃圾，然后静默丢弃。

**证据**：把真实抓到的 190 字节 chunk 回放，对比两种做法：

| 做法 | 解出的包 |
|---|---|
| 一次性 push（旧） | `id=0x3`（Set Compression）✓ + `id=0xac`（185 字节垃圾）✗ |
| 边解边处理（新） | `id=0x3` ✓ + `id=0x1`（Encryption Request，172 字节）✓ |

**修复**：`PacketDecoder.push()` 增加即时回调，每解出一包就立刻交给上层，上层更新 `threshold` 后剩余字节才用新阈值继续解。

```js
// ✅ 新代码：边解边处理
this.decoder.push(plain, (p) => this.handlePacket(p));
```

这也解释了"为什么之前真机测试是通过的"—— 那次测试里两个包恰好落在不同的 TCP 段，侥幸没触发。

### 其余修复项

| 层 | 问题 | 修复 |
|---|---|---|
| `proto.js` | `inflateSync` 抛出的异常会穿透 drain 循环，导致缓冲区与已消费帧错位 | try/catch + `err.code = 'BAD_ZLIB'`，上层据此断开 |
| `proto.js` | 解压后长度不符时静默忽略 | 记录 `lastWarn` 并返回数据（部分服务端会算错） |
| `nbt.js` | 定点读取越界时抛 Node 原生 `RangeError`（`offset is out of range`，无法定位） | 统一 `_need()` 前置检查，抛可读中文错误 |
| `nbt.js` | 恶意服务端可用超深嵌套 compound/list 打爆调用栈 | 加 512 层嵌套上限 |
| `nbt.js` | `BYTE_ARRAY` 返回 `subarray`（视图，不是副本） | 改 `Buffer.from()` 拷贝 |
| `crypt.js` | `Buffer.from(serverId,'latin1')` 对 >0xFF 字符**静默截断**，算出与服务端不一致的 hash 却毫无提示 | 显式校验，越界直接抛错 |
| `crypt.js` | RSA 明文超长时报错信息是 `data too large for key size`，看不懂 | 提前按模长算上限（PKCS#1 是 模长-11），抛中文可读错误 |
| `crypt.js` | `joinMojangSession` **没有超时** —— 网络卡住会让整个连接永久挂起 | 加 15 秒 `AbortController` 超时 |
| `crypt.js` | `EncryptedSocket` 用 `!this.enabled` 判断旁路，任何 falsy 值都会静默跳过一次加密，导致 CFB8 流状态永久错位 | 改 `=== false`，只有显式关闭才旁路 |
| `auth.js` | 所有网络请求无超时 | 统一 `fetchWithTimeout()`（20 秒） |
| `auth.js` | 回调端口被占用时只抛 `EADDRINUSE` | 给出人话提示 + 排查命令 |
| `auth.js` | XSTS 401 是最常见的正版登录失败，却只抛原始 HTTP 错误 | 翻译 `XErr` 错误码（无 Xbox 档案/未成年/地区限制…） |
| `auth.js` | `waitForCode()` 可能先 reject 而产生 unhandledRejection | 挂空 catch |
| `auth.js` | 凭据文件直接覆盖写，崩溃会留下半个 JSON → 凭据凭空丢失 | 临时文件 + `rename` 原子写 + `0600` 权限 |
| `auth.js` | 授权未返回 `refresh_token` 时，会用 `undefined` 覆盖掉原本可用的凭据 | 加保护，不再写入无效值 |
| `app/main.js` | 连点"连接"会并发建连，后者覆盖 `client` 变量，前者变成野连接（**持续占用服务器名额**） | 加 `connectBusy` 互斥锁 |
| `app/main.js` | 状态轮询定时器用局部变量持有，换连接时旧定时器泄漏 | 提升为全局 `pollTimer` + `stopPoll()` |
| `app/main.js` | 旧连接的回调会误操作新 `client` | 闭包持有 `self` + `isCurrent()` 校验，过期事件一律丢弃 |
| `app/main.js` | 账号登录可重入，并发抢占同一回调端口 | 加 `loginBusy` 互斥锁 |
| `client.js` | `startKeepAliveLoop()` 重复进入 play 会叠加两个定时器 | 幂等（先清旧定时器） |
| `client.js` | 保活定时器在 socket 死亡后仍空转 | 自检并自行 `clearInterval` |
| `renderer.js` | 删除服务器用闭包里的旧下标 → **删错服务器** | 按对象身份重新 `indexOf` 定位 + 修正选中态 |
| `renderer.js` | 快速切换服务器时，旧的 ping 响应会覆盖新选中项的信息 | 加 `pingSeq` 序号，只认最后一次 |
| `renderer.js` | `toast()` 先 `remove('hidden')` 再设 `className`，后者会覆盖前者 → **第二次以后的提示永远不显示** | 调整顺序：先设 `className` 再 `remove` |

## ❗ 第二关键 BUG：打包后 `Unknown cipher`（2026-10-07 第三轮）

**症状**（用户实测日志）：

```
[验证] Mojang 登记成功，服务端将反查并放行
[验证失败] Unknown cipher
```

注意：**Mojang 登记是成功的** —— 说明整条正版认证链、RSA 握手、serverId 签名**全对**。
死在最后建立加密流那一步。

### 根因：Electron 用的是 BoringSSL，没有 CFB8

Minecraft 加密固定用 **AES-128-CFB8**。但 `crypto.createCipheriv('aes-128-cfb8')`
**在不同运行时可用性不一样**：

| 运行时 | 底层加密库 | 有 `aes-128-cfb8`? | cipher 总数 |
|---|---|---|---|
| 系统 Node 22（开发/自检） | OpenSSL 3.5 | ✅ 有 | 很多 |
| **打包后的 Electron 33** | **BoringSSL** | ❌ **没有** | **仅 28 个** |

Electron 为减小体积用 BoringSSL，**裁掉了 CFB8 模式**。所以：

> **命令行 `node src/selftest.js` 永远全绿，一打包成 exe 就必然失败。**

这个坑极其阴险，因为：
1. 报错点是 `createCipheriv`，看起来和"加密握手逻辑"无关，容易查错方向
2. **所有已有的测试自己也在用 `createCipheriv('aes-128-cfb8')`** —— 测试和被测代码犯了同一个错，
   导致测试在 BoringSSL 下**自己先崩**，根本没能力发现这个问题
3. 开发环境永远复现不了

实测证据（用打包后的 exe 跑探针）：

```
运行时：node=20.18.3 electron=33.4.11 openssl=0.0.0   ← BoringSSL，openssl 版本报 0.0.0
原生 cfb8 可用？false
可用 cipher 只有 28 个：aes-128-cbc, aes-128-cfb, aes-128-ctr, aes-128-ecb,
  aes-128-gcm, aes-128-ofb, ..., rc4        ← 注意：有 cfb，但没有 cfb8
```

### 修复：手写 CFB8 回退（与 node-minecraft-protocol 官方做法一致）

参考 `PrismarineJS/node-minecraft-protocol` 的 `encryption.js`：

```js
function createCipher (secret) {
  if (crypto.getCiphers().includes('aes-128-cfb8')) {
    return crypto.createCipheriv('aes-128-cfb8', secret, secret)  // 环境支持就直接用
  }
  return new Cipher(secret)                                        // 否则手写 CFB8
}
```

我们在 `src/crypt.js` 里实现了同样的回退，底层依赖 **`aes-128-ecb`**（BoringSSL 保留了这个）：

```
CFB8 加密一个字节 P：
  a. 对当前 16 字节移位寄存器做 AES-ECB 加密 → 取首字节 K
  b. 密文 C = P XOR K
  c. 寄存器左移 1 字节，尾部补入 C（**补的是密文**，加密解密都一样）
```

> ⚠️ **最容易写错的地方**：CFB8 的密钥流**每个字节都要重算**（因为寄存器每处理一个字节就变了）。
> 只有 **CFB128** 才是每 16 字节重算一次。我第一版就按 CFB128 的节奏写了，
> 结果「第一字节对、第二字节开始全错」—— 这个特征很有辨识度，记下来。

现在统一走 `createCipher()` / `createDecipher()` 工厂，自动选实现。

## 登录方式大改：从「授权码流」换成「设备代码流」（2026-10-07 第二轮）

**报错原文**：

```
我们无法完成你的请求
invalid_request: The provided value for the input parameter 'redirect_uri'
is not valid. The expected value is a URI which matches a redirect URI
registered for this client application.
```

### 第一次诊断（错的，留作教训）

第一轮我以为问题是"端口带不带"。那一版的结论是：注册值是 `http://localhost/auth-response`（无端口），
代码用了带端口的 `:25580`，所以被拒。于是改成"先探端口再拼 URL"，优先用无端口形式。

**这个结论是错的。** 用户随后贴出了真实浏览器地址栏，里面已经是
`redirect_uri=http%3a%2f%2flocalhost%2fauth-response`（**无端口**）——**照样被拒**。

**我为什么会误判**：我只看了第一跳的 302 就当成"通过了"。实际上
`login.microsoftonline.com/consumers/oauth2/v2.0/authorize` 对**任何**请求都先返回 302，
跳到 `login.live.com/oauth20_authorize.srf` ——**真正的校验发生在第二跳**，而我根本没跟过去看。

> 教训：**跟随重定向链时，必须跟到终点再下结论**。中间那一跳的 3xx 只代表"转发"，不代表"通过"。

### 第二次诊断（正确，逐跳实测）

用合法的 43 字符 PKCE challenge（长度不合法的 challenge 会让微软先报
`AADSTS501491`，从而**掩盖** redirect 校验结果，这一点也踩过）逐个实测：

| 候选 redirect_uri | 第一跳 | 第二跳真实结果 |
|---|---|---|
| `http://localhost/auth-response` | 302 | ❌ invalid_request |
| `http://localhost:25580/auth-response` | 302 | ❌ invalid_request |
| `http://localhost:8080/auth-response` | 302 | ❌ invalid_request |
| `http://127.0.0.1/auth-response` | 302 | ❌ invalid_request |
| `https://localhost/auth-response` | 302 | ❌ invalid_request |
| `http://localhost/auth-response/` | 302 | ❌ invalid_request |
| `https://login.live.com/oauth20_desktop.srf` | 302 | ✅ 到达登录页 |

**所有 localhost 回调一律被拒**，只有微软自己的 `desktop.srf` 能过。
再拿一个纯 UUID 格式的假 client_id 做对照组，它在三个地址上**全部失败** ——
证明这个探测方法本身是有区分度的，不是"什么都报错"。

### 真正的根因

继续挖，设备代码接口直接把底牌翻出来了：

```
POST https://login.microsoftonline.com/consumers/oauth2/v2.0/devicecode
→ 400 AADSTS700016: Application with identifier '00000000402b5328'
  was not found in the directory '9188040d-6c67-4c5b-b112-36a304b66dad'.
```

**这个公开 client_id 在 `microsoftonline.com` 目录里根本不存在。**
它是 `login.live.com` 体系下的老式应用 —— 两个端点**不是同一套注册表**。
所以：

- 走 `microsoftonline.com` 的授权码流 → 它只能认得 `login.live.com` 那边注册的 `desktop.srf`，而那个地址**收不到本机回调**
- 走 `login.live.com` 自己的接口 → **完全正常**

### 修复：改用设备代码流（device code flow）

实测 `login.live.com` 的设备代码接口一路畅通：

```
POST https://login.live.com/oauth20_connect.srf
→ 200 { user_code: 'MEU23V6D', verification_uri: 'https://www.microsoft.com/link',
        device_code: '...', interval: 5, expires_in: 900 }

POST https://login.live.com/oauth20_token.srf   （用户尚未授权时）
→ 400 { error: 'authorization_pending' }        ← 预期内，证明链路是通的
```

这套端点与 **PrismarineJS/prismarine-auth 的 `live` flow 完全一致**
（`deviceCodeRequest` / `tokenRequest`），是这个领域久经考验的做法。

**设备代码流的好处**：

- **根本不需要 `redirect_uri`** → 整整一类回调问题从此消失，也不可能再有"端口被占"
- 用**同一个 client_id** `00000000402b5328` 就能跑通（实测）
- 用户操作也不麻烦：浏览器打开 `microsoft.com/link`，输入 6~8 位短码，点允许

**代价**：设备码 15 分钟过期；轮询有最小间隔（5 秒）。两者代码里都已正确处理
（过期主动结束、`slow_down` 自动放慢）。

### 界面配合

设备代码流的用户要「看代码 → 去浏览器填」，代码漏看就白等一场。所以界面上加了一个
**高亮提示条**：大号等宽字显示短码、一键复制、验证网址可点「重新打开」。
代码从授权日志里解析出来（`输入代码：XXXX` / `打开网址：https://...`），
UI 自检里专门验证了这条解析链路不会静默失配。

### 测试

## 它到底是怎么工作的

```
你的程序
   │  TCP 连到服务器
   ▼
握手   告诉服务器「我是 26.2，要登录」
   │
登录   Login Start（用户名 + UUID）
   │   ├─ online-mode=false → 服务器直接回 Login Success
   │   └─ online-mode=true  → Encryption Request → 加密握手 → Login Success
   ▼
配置   Registry Data / Known Packs / Finish Configuration
   │   （这一阶段 26.x 才有，很多老教程会漏掉 → 卡在"配置阶段无响应"）
   ▼
Play   保活应答 + 坐标回执 + 聊天收发
```

**复用的是游戏自己的协议**，不是外挂式注入：

- ✅ 只走官方网络协议 + 官方微软 OAuth —— 和真实客户端同一条路径
- ❌ 不注入游戏进程
- ❌ 不读写游戏内存
- ❌ 不修改任何游戏文件
- ❌ 不需要开游戏

## 26.2 的几个坑（我都踩过了）

| 坑 | 真相 |
|---|---|
| 标准 mineflayer 能直接用吗 | **不能**。官方仓库 issue #3893 就是有人卡在这，26.x 的 `minecraft-data` 还没进主分支 |
| Login Start 要不要带 UUID | **要**。26.2 的 `login_start` 字段是 `username + playerUUID`，缺了服务器直接拒 |
| 有没有配置阶段 | **有**，而且必须回 `Finish Configuration`，否则永远进不了游戏 |
| 聊天是 JSON 还是 NBT | **26.x 是 NBT**，不是 JSON。按老教程解析 JSON 会得到乱码 |
| 位置包格式 | 26.x 的 `position` 包结构变过，本工具做了容错解析 |
| 26.2 有混淆吗 | **没有**。26.x 的 `version_manifest` 不再提供 `client_mappings`，类名就是真名 |

**所以这个工具是自己实现的协议层**，运行时不依赖任何第三方 Minecraft 库。

```bash
npm run dist         # 产出 dist/*.exe（便携版 + 安装版）
```

用的是 `electron-builder`。便携版单文件双击即跑，安装版会创建开始菜单与桌面快捷方式。

---

## 环境

- **Node.js ≥ 18**（本机 v22.22.2）
- 运行时**零第三方依赖** —— 只用 Node 内置的 `net` / `crypto` / `zlib` / `dns` / `fetch`
- 打包时用 `electron` + `electron-builder`
- 支持版本：**MC 26.2（协议 776）**

换其他版本要改 `src/proto.js` 里的 `PROTOCOL_VERSION` 和 `PACKET_ID` 表 —— 从 `minecraft-data` 的对应分支提取即可。

## ⚠️ 必须说清楚的风险

**服务器管理员能看见你。**

这不是"隐身"工具。服务端日志会如实记录：

```
BaiXu[/127.0.0.1:3168] logged in with entity id 1
```

管理员的视角里，这就是一个叫 `BaiXu` 的玩家上线了。区别只在于：

| 特征 | 真实客户端 | 本工具 |
|---|---|---|
| 会移动吗 | 会 | **不会**（一直站在原地） |
| 会响应动作吗 | 会 | 不会 |
| 服务端留记录 | 是 | **是** |
| 需要开游戏 | 是 | 不用 |

**很容易被认出来是个 bot：** 一个从不移动、不环顾、只回保活的玩家 —— 任何有经验的管理员一眼就能看出来。

**正版验证模式下还多一层：** 用的是**你自己的真实账号**。任何违规行为都直接记在你账号头上，没有"小号背锅"的余地。

**使用建议：**
1. 只在自己有权限的服务器上用（自建服 / 局域网 / 朋友私服）
2. 挂机前先跟服主说一声
3. **不要**在公开服务器上用，可能违反服务条款被永久封禁
4. 正版模式尤其注意：**别拿主账号去公开服试**

技术上它是合法协议客户端；**是否使用，取决于你是否得到了服务器所有者的许可。**

## 常见问题

**Q: 正版登录点了没反应 / 浏览器没打开？**
看日志区的提示。若浏览器没自动开，复制日志里的授权链接手动打开也行。授权完成后程序会自动继续。

**Q: 提示"尚未登录微软账号"？**
勾了「正版验证登录」但还没登录账号。先点「登录微软账号」完成授权。

**Q: 每次都要重新授权吗？**
不用。access_token 有效期约 24 小时，`refresh_token` 长期有效。程序每次连接前会自动静默续期 —— **正常情况下你只需要授权一次**。

**Q: 提示"连接超时"？**
检查地址端口，确认服务器在跑。域名服务器会自动查 SRV 记录。

**Q: 这个账号需要拥有 Minecraft 吗？**
**需要**。微软账号必须在 `api.minecraftservices.com` 上验证拥有 Java 版 Minecraft，否则第 4 步会失败。

**Q: 进去了但一直不动 / 好像没反应？**
正常。它只维持连接，不模拟移动。

**Q: 想让它掉线后自动重连？**
`config.json` 里 `"reconnect": true`，配合 `reconnectDelaySec` 设置间隔。

**Q: 能同时挂多个服吗？**
开多个窗口各连一个即可。

**Q: 凭据存在哪？安全吗？**
`%APPDATA%\.mc-noclient\accounts.json`。里面是 refresh_token —— 等同于该账号的 Minecraft 登录权限，**别把它发给别人**。点「退出账号」会清除。

**Q: 想支持别的 MC 版本？**
改 `src/proto.js`：`PROTOCOL_VERSION` + `PACKET_ID` 表。包 ID 从
`https://raw.githubusercontent.com/PrismarineJS/minecraft-data/<分支>/data/pc/<版本>/protocol.json` 提取。
配置阶段是 1.20.2+ 才有的，更老的版本流程不一样。
